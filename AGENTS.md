# SolvencyLoop conventions

The application was migrated from an AI Builder Vite/Express export to the Next.js 15 App Router requested by the user. The old preview server is no longer active.

- Runtime: Next.js 15, React 19, TypeScript, Tailwind with existing Tatum tokens.
- The user-supplied consumer design reference controls the visual theme: neutral sky-blue canvas across both routes, clear form sections, bold real balances, pill controls and a glass proof drawer. Keep generated token sources intact; local overrides live in consumer-theme.css and workspace.css. Preserve reduced-motion support and never introduce the reference's example wallets, amounts, memories or transaction handlers.
- `/` is the public explanatory landing page; `/app` is the mandatory-onboarding workspace. Preserve redirects for older `/?split=` links. Landing illustrations are conceptual graphics, never application fixtures. Framer Motion presentation must hydrate consistently. Vanta fog is decorative feedback only: green success, yellow pending, red attention; unresolved errors/confirmations override a prior success. Keep pause, hidden-tab cleanup, reduced-motion/data-saver support and the static WebGL fallback. Never infer transaction success from an animation.
- Read `.claude/skills/tatum/SKILL.md` before changing blockchain integration and `.claude/skills/tatum-design/SKILL.md` before changing UI. These directories are managed; do not edit them.
- Search suggestions use actual saved contacts or loaded bills. Require an explicit choice; editing a selected contact clears it until another selection. Preserve keyboard navigation, wallet references, disabled states and visible account-wide consent. Loading reflects real work, with no invented percentages. Keep public content readable without JavaScript and old bill links as HTTP redirects.
- Component visual fixtures belong only in tests and are served through Playwright interception, never a guest or preview route. They cannot sign or send live transactions.
- No application database or durable local user-state store. Profiles, contacts, splits, and cooldown vaults live in the Sui Move package; behavioral memory uses MemWal/Walrus.
- One published package creates independent objects. The shared SolvencyRegistry stores only wallet-to-profile IDs and the user count; only first registration writes it. UserProfile is a non-transferable wallet-owned object with only `key`. Profile/contact updates and financial entries take the owned profile directly, verify its recorded wallet, and never write the global registry. Discover profiles through the directory and verify exact type, UID, address owner and wallet; lookup errors must not enable fresh registration.
- Application Sui traffic must use the fixed authenticated Tatum Mainnet gateway at its supported `/graphql` path; the deprecated JSON-RPC root returns 404. Browser calls use `/api/tatum-rpc`; server code and app readiness scripts use the shared transport. Preserve the official GraphQL Core API and compatibility facade, in-flight read coalescing, request pacing and read-only Retry-After handling; never automatically retry signed execution mutations. By the user's explicit preference, manual Sui CLI contract deployment and source verification use Sui's direct Mainnet endpoint, without the Tatum bridge. Keep the pinned MemWal client-injection patch intact and retest it on upgrades.
- No demo contacts, preset bills, seeding actions or minimum seeded-memory requirement. Onboarding must work with an empty owned MemWal account. Bills support 1–64 participants, exact equal/custom shares and explicit user payment preferences.
- Never expose delegate private keys, Tatum keys, or embedding API keys with `NEXT_PUBLIC_*`. Private values belong in ignored `.env.local` or host secrets.
- Only real user-provided canonical Mainnet wallets and native Circle USDC. Test fixtures belong only in tests; no mock fallback data in runtime code.
- Use bigint micro-USDC arithmetic. The Move contract is the authority for payment, escrow, authorization, reserve, and cooldown invariants.
- Memory requests require a wallet personal-message signature over the action/payload, timestamp, nonce, and origin, or a payload-bound request signed by an in-memory browser key under an exact-wallet/account/origin wallet grant lasting at most one hour. Headless incoming work requires that owner's own current funded allowance and incoming consent. Do not remove authentication or silently convert relayer failures into empty successful data.
- Each user owns their MemWal account. Discover it from the configured AccountRegistry, verify owner/type/active delegate on every memory request, and use the account linked in that wallet's on-chain profile. Never restore a global account fallback or write into another user's account from a caller's signature. Protocol package/registry IDs and the app's server delegate remain shared.
- Decode MemWal delegate `public_key` byte vectors from canonical Base64 in GraphQL Move JSON, retaining numeric-array compatibility for legacy readers/tests. Require exactly 32 valid bytes and the expected public key plus derived delegate address. Never mistake an encoding mismatch for a missing account or permission grant.
- MemWal onboarding is mandatory: hide the application until the user has an owned active MemWal account, authorized the app, and linked it through registration. Move registration must accept a genuine MemWalAccount object, never a plain address. All financial functions must verify ownership and the registered account link. Only cancellation, refunds and matured withdrawals may proceed with an inactive/revoked memory account, and still require the actual owned linked account. There is no payment or guest-use bypass. All payments are native Circle USDC; SUI is used for network gas.
- The vendored MemWal production source is pinned; only test-only fixture helpers are added. Review its source, Mainnet dependency binding and Move.lock together. Keep dependency verification enabled for publishing. The readiness check must validate current function argument shapes, including MemWalAccount references, not merely function names.
- Check `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, and both Move commands when their corresponding code changes. Stop dev before production builds; do not run both against the same .next directory.
- Primary compiler/CLI/VM baseline: official Sui 1.82.3, matching framework revision bf4073918ed33cfa0b09c500658fa116a774bcfd in both Move manifests and lockfiles. Use project commands (`npm run sui`, `move:build`, `move:test`, `move:verify-bundle`) to avoid an older global VM. `npm run move:verify-deps` isolates the 1.72.2 read-only dependency verifier because that interface was removed from the newer CLI; never use the old VM for tests. Project publish/upgrade commands run this actual preflight before execution. Preserve dependency verification, check in lockfiles and review framework/toolchain changes together. No global CLI/PATH replacement or bypass flag. See MOVE_DEPLOYMENT.md.
- No deployment, signing, or live financial transaction is implied by a request to build/test. The original core is published; the optional autopilot extension requires an owner-operated compatible upgrade and a new AgentDirectory. Read-only checks and unsigned simulations are allowed for verification. Users explicitly approve onboarding, delegate/session grants and funded allowance policies. Only thereafter may the configured dedicated executor handle eligible commands and incoming shares within the live allowance's account, executor, epoch, payee, expiry, native-USDC and spending limits. Keep the executor disabled during development; never enable/fund/deploy it as part of automated tests. Owner revocation and withdrawal must stay available independently of routine pending work and memory delegate activity. See AUTOPILOT_GUIDE.md.

See README.md for setup, deployment, and validation.
